# Lemon UI 自定义契约

主题覆盖、多端尺寸集中管理和固定解析优先级同时遵守 [主题与尺寸架构](theme-architecture.md)。

本文用于避免组件库在追求后台页面开发速度时，退化为只能使用固定预设、难以自由组合的封闭 UI 套件。

## 一、对 lemon_shadcn 评价的结论

参考评价中值得保留的能力：

- 标准表单、列表、详情、表格和弹层可以快速搭建。
- 控件高度、字号和间距具有统一默认值，常规页面自然对齐。
- 可以嵌入现有 Flutter 应用，不强制替换应用根组件。
- 表单验证、异步保存和编辑状态能够共享尺寸规则。
- 主题能够在局部子树覆盖。

需要明确消除的问题：

- 公开控件只是第三方库的别名，结构和能力被上游 API 锁死。
- 固定槽位、内置留白、顶对齐和编辑态最小高度等布局规则隐藏在实现中。
- 构造参数、组件主题和 builder 的自定义入口没有统一层级。
- 容器通过识别某个特定子控件类型来修正高度或光学间距，任意 Widget 无法获得同等待遇。
- 表格、图表和基础控件来自不同视觉源，修改一套主题不能稳定影响其他部分。

Lemon UI 的目标不是只适合统一后台界面，也不是无限抽象的底层渲染框架，而是同时提供：

1. 默认值完整、代码量少的常规页面开发体验。
2. 可检查、可覆盖、可绕开的设计系统能力。
3. 手机、平板、桌面和手表各自明确的尺寸方案。
4. HyperOS 风格默认视觉，但不将默认视觉写死为唯一结构。

## 二、禁止公开别名组件

- 不使用 `typedef HyperXxx = ThirdPartyXxx` 作为公开控件实现。
- 允许在内部组合 Flutter 或第三方控件，但 `HyperXxx` 必须拥有独立、稳定且经过测试的公开 API。
- 上游没有暴露所需能力时，可以局部重写，不允许把第三方限制伪装成 Lemon UI 的设计规则。
- 第三方升级不得直接改变 Hyper 控件的尺寸、语义、主题解析或插槽行为。
- 仅做平台能力连接的适配器应放入 integration 或 adapter 层，不冒充基础控件。

## 三、布局契约必须显式

每个控件的文档和 Demo 必须说明以下适用项：

- 外部尺寸：固定、最小、最大还是由内容决定。
- 内容槽位：约束、对齐、默认间距和是否允许换行。
- 内边距、外边距和光学修正分别来自哪个属性。
- 单行、多行、loading、错误和编辑状态是否保持尺寸稳定。
- 文字放大、RTL、窄宽度和无限约束下的行为。
- 视觉尺寸与命中区域是否分离。
- 哪些默认值来自全局基础主题，哪些来自控件主题，哪些属于变体配方。

实现中不得存在无法通过公开属性或主题解释的固定留白、偏移和最小高度。确有必要的内部常量必须成为有名称、有测试的默认值，并在对应控件文档中说明。

## 四、统一自定义入口

所有控件按同一顺序提供自定义能力：

```text
开箱即用默认值
→ .xx 变体或语义构造器
→ 高频实例属性
→ 完整 HyperXxxStyle
→ 全局或局部 HyperXxxTheme
→ 明确命名的内容槽位
→ 必要时提供状态 builder
→ 直接使用 Flutter 原生组件自由组合
```

规则：

- 高频实例属性、完整样式和主题中的对应字段保持同名、同类型、同语义。
- builder 不是修改颜色、圆角或间距的必经入口。
- 没有 builder 时，文档必须明确现有插槽能否替换结构；不能让调用方靠试错判断。
- 高级入口不能削弱普通入口的无障碍、焦点、键盘和异步能力。
- 调用方可以绕过高级组合控件，使用同一套 Hyper 基础主题和原生 Widget 新写控件。

## 五、插槽对任意 Widget 一视同仁

- 父控件不得通过 `child is HyperXxx`、runtimeType 或私有标记为特定子控件增加间距、高度或对齐。
- 插槽只通过公开的 `BoxConstraints`、对齐、内边距和语义契约约束内容。
- 库内控件和外部 `Text`、`Icon`、自定义 Widget 放入同一插槽时遵守相同布局规则。
- 特殊光学对齐使用插槽自己的显式属性，例如 `contentAlignment`、`slotPadding`、`baseline`，不能藏在子控件识别逻辑中。
- 若某个组合需要协同行为，应提供公开协议、controller 或专用组合控件，不使用隐式类型特判。

## 六、第三方视觉源必须经过适配

表格、图表、编辑器、日历等复杂能力可以使用第三方实现，但必须建立明确边界：

- 每个第三方能力具有独立的 `HyperXxxAdapterTheme` 或映射函数。
- 颜色、字体、边框、圆角、行高、选中态和动画从 Hyper 主题显式映射，不依赖第三方默认主题碰巧一致。
- 映射不到的能力必须记录为适配限制，不能宣称会自动跟随全局主题。
- 第三方控件不得读取另一个 Hyper 控件主题作为自己的视觉来源。
- 更换第三方实现时，业务层使用的 Hyper API 和主题字段尽量保持稳定。
- 对体积较大或平台受限的第三方能力优先放入可选包，避免污染核心包依赖。

## 七、默认对齐但不使用倍率密度

- 使用 `HyperSizeScheme` 为不同终端提供明确数值，不使用 density 或 scale 乘数。
- 表单、按钮、选择器等可以共享全局基础高度作为回退，但每个控件主题都能覆盖自己的明确高度。
- 紧凑后台布局通过桌面尺寸方案或显式 small 尺寸档实现，不通过隐藏缩放压缩全部属性。
- 页面局部变高、变窄时设置控件属性或局部控件主题，不依赖外层 Padding 抵消内部未知留白。
- 组合控件负责公开自己的行高、槽位高度和内容对齐，不能假设所有子控件都有相同内部结构。

## 八、每个控件的能力表

每实现一个控件，必须在组件目录或 Demo 中列出：

| 能力 | 必须说明的内容 |
|---|---|
| 变体 | 所有 `.xx` 构造器及其语义 |
| 尺寸 | 默认来源、明确档位、实例覆盖和命中区域 |
| 样式 | 高频属性与完整 `HyperXxxStyle` |
| 主题 | 公共样式、变体样式、局部主题和解析优先级 |
| 状态 | hovered、focused、pressed、disabled、loading 等适用状态 |
| 内容 | 默认内容、命名插槽、任意 child 和互斥规则 |
| 布局 | 约束、留白、对齐、换行、溢出和尺寸稳定策略 |
| 行为 | 回调、controller、受控与非受控模式 |
| 高级扩展 | builder 能改变的层级及无法改变的部分 |
| 无障碍 | 语义、键盘、焦点、RTL、文字缩放和减少动画 |
| 第三方依赖 | 是否存在、主题映射范围和已知限制 |

缺少某项能力是允许的，但必须明确“不适用”或“暂不支持”，不能通过隐含行为代替说明。

## 九、实现验收清单

一个控件完成前至少确认：

- 不依赖公开 typedef 别名。
- 没有基于子控件具体类型的布局特判。
- 所有固定尺寸和留白都有公开来源。
- 实例样式与控件主题能够逐字段对应。
- 全局、局部主题和实例覆盖均有测试。
- 任意 Widget 插槽至少有一个测试。
- 变体和主要状态在 Demo 中可见。
- 显式尺寸不会被设备类型或缩放倍率改写。
- 第三方视觉能力具有显式主题映射测试。
- 高级自定义失败时，调用方仍能使用基础主题和原生组件自由实现，而不需要修改核心控件。
- 常规视觉优先由单个 `Container` 或 Material 基础控件完成，没有可合并的重复包装。
- 同一边界最多主动裁切一次；只有玻璃采样、异形或调用方明确要求时才增加裁切。
