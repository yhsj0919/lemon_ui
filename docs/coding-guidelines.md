# Lemon UI 编码规则

组件实现同时遵守 [主题与尺寸架构](theme-architecture.md)：设备尺寸统一由主题管理，组件内部不得保存或选择各端尺寸常量。

本文档约束 Lemon UI 的实现、测试和代码审查。目标是让代码直接、轻量，并方便程序员阅读、调试和后期人工修改。

## 核心原则

### 不写过度防御性代码

- 只处理已经明确的需求、真实存在的边界和能够复现的问题。
- 不为假设中的未来问题预先增加包装层、占位节点、状态、分支或兜底逻辑。
- 修复问题时优先消除根因，不通过固定尺寸、固定行高、维持相同组件树等手段掩盖现象。
- 需要兼容异常输入时，优先使用清晰的断言、类型约束或公开契约，不静默修正调用方数据。
- 防御逻辑必须能说明具体风险；无法说明用途的防御逻辑应当删除。

### 代码必须方便人工修改

- 优先使用 Flutter 原生控件直接组合，能用一层完成就不增加第二层。
- 控制流保持线性，避免不必要的抽象、辅助类和间接调用。
- 名称表达业务或视觉含义，不使用含糊缩写。
- 默认值集中在对应控件或主题中，避免同一规则散落在多处。
- 重要尺寸和视觉属性必须能从公开属性或主题追踪到最终绘制。
- 小尺寸、比例敏感控件不得为了统一而回退到全局基础圆角；应保留控件自身几何，并允许对应控件主题和实例覆盖。
- 不为了减少少量重复而引入难以理解的通用抽象；只有规则真正稳定且被多处复用时才提取。
- 注释解释设计原因和约束，不复述代码本身。
- 公开控件、主题和样式的每个属性都使用中文文档注释说明用途；存在继承、显式关闭、布局影响或取值范围时必须一并写明。
- 局部变量只在算法或设计原因不直观时注释，不为显而易见的赋值堆叠说明。

## 组件实现

- 组件树只包含布局、绘制、语义或交互所必需的节点。
- 普通模式不创建高级模式专用的空占位层；需要时按状态直接创建对应节点。
- 视觉效果不得意外参与内容布局。例如装饰性边框应只负责绘制，不应改变文字或图标的可用空间。
- 拥有圆角形状的容器默认按自身形状裁切子内容，避免悬停、按压等状态层越过边界；需要内容越界时必须显式关闭裁切。
- 点击区域与视觉尺寸不同时，可以保留一层职责明确的约束或居中节点。
- 不使用固定行高、额外偏移或透明占位修复布局抖动，除非该数值本身就是公开设计规范。
- 新增抽象前先确认原生控件组合无法清晰完成需求。

## 测试规则

- 测试用户可观察行为和公开契约，不绑定无关的内部组件树结构。
- 一个问题只保留一组最小且有意义的回归断言。
- 尺寸问题验证最终尺寸或坐标；绘制问题验证对应样式；交互问题验证状态和回调。
- 除非节点身份属于公开契约，否则不要断言 Element、包装层数量或无关控件类型保持不变。
- Demo 测试确认页面可用和功能可见，组件细节由组件测试负责，避免重复像素级断言。

## 修改检查

提交实现前检查：

1. 是否修复了根因，而不是遮盖现象？
2. 是否加入了当前需求不需要的包装层或分支？
3. 删除某段兜底逻辑后，是否仍满足公开契约？
4. 下一位程序员能否从局部代码直接看懂数据和样式如何生效？
5. 测试是否关注行为，而不是偶然的内部实现？
