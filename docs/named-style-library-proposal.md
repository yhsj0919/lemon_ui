# 新组件库：命名样式与主题交付方向

记录日期：2026-11-06。

本文记录需求讨论，供后续可能新建的独立组件库继续设计。尚未开始实现，文中的 API 和数据结构均未定稿；本文不修改现有 Lemon UI 的主题架构或组件行为。

## 背景与目标

同一个软件中，同一种控件可能需要多种外观。例如搜索框、普通表单输入框、表格内输入框和登录输入框需要同时存在，一套组件主题难以直接满足。

新体系应支持每种控件拥有多套可命名、可复用的样式配置。业务代码引用约定名称，设计师通过主题编辑器维护这些样式，导出主题包，业务端动态导入后自动更新引用它们的控件。

## 用户已明确的方向

- 保留现有组件库，另做一套新控件；新体系暂时不考虑兼容现有主题、Style 和组件接口。用户可能新建独立仓库处理，仓库与包名尚未确定。
- 控件功能是既定的，由代码和公开参数实现，主题不能修改控件功能。
- 同一种控件支持多套命名样式，并能在同一页面同时使用。
- 控件使用时指定样式名称；支持约定名称或预设名称，导入对应主题后自动改变外观。
- 设计师在主题编辑器中编辑、导出主题，业务端导入使用，形成完整交付流程。
- 支持动态导入。此处指运行时加载样式数据，具体文件格式、加载接口和更新机制待设计。
- 不要求内置手机、平板、桌面、手表的四端规格体系。需要不同端外观时，可分别创建命名样式；多个端也可以共用样式。
- 平台差异只是命名样式的一种用途，核心需求是同一个软件内的多种外观共存。

## 使用与交付示意

以下仅表达意图，`NewTextField`、`NewButton` 和 `styleName` 均为占位名称：

```dart
NewTextField(styleName: 'input.search', ...)
NewTextField(styleName: 'input.form', ...)
NewTextField(styleName: 'input.table', ...)
NewButton(styleName: 'button.primary', ...)
```

1. 项目约定或选用预设样式名称。
2. 业务代码为控件指定名称，并配置其功能参数。
3. 设计师在主题编辑器中维护对应样式的视觉配置。
4. 设计师导出主题包，交付给业务端。
5. 业务端导入主题包，按名称匹配样式，相关控件自动更新外观。

例如更新 `input.search` 应影响引用该名称的输入框，不应同时改写 `input.form`。外观更新不应重置控件已有的输入内容、焦点或业务状态。

## 样式职责

样式描述控件既有结构和状态的视觉表现，例如文字、占位文字、图标、光标、颜色、尺寸、间距、边框、圆角、阴影、材质，以及默认、悬停、聚焦、按下、错误、禁用等适用状态的外观。

控件功能、事件、数据、校验规则及交互逻辑仍由控件代码和业务参数确定。具体可配置字段应按各控件职责设计，不将动态样式包扩展为动态功能或任意 UI 结构执行系统。

## 已讨论但尚未确认的建议

- 样式契约区分稳定标识、设计师可读的显示名称和控件类型；显示名称可以修改而不影响业务引用。
- 组件配置保持强类型，动态名称只用于定位对应类型的样式配方。
- 主题包可以包含全局语义颜色、字体等公共值，命名样式既可引用公共值，也可显式覆盖。
- 使用带版本号的 JSON 作为首版导出格式。
- 导入先校验，再整体提交；失败保留当前主题，避免部分更新。
- 支持业务端提供所需样式清单，设计师在编辑器中按清单配置。
- 先用一个控件验证多套样式共存、编辑导出、动态导入和更新，再扩展其他控件。

以上是讨论中的方案建议，不代表用户已确认具体实现。

## 后续需要确定

- 是否新建仓库、包名、控件命名及首批控件。
- 样式命名规则、预设清单，以及契约的生成与校验方式。
- 主题包的数据模型、版本兼容和迁移规则。
- 样式缺失、名称重名、类型不匹配及未知字段的处理方式。
- 导入采用整体替换、增量合并，还是显式支持两种模式。
- 是否支持基础样式继承、局部作用域、别名映射和实例视觉覆盖，以及它们的优先级。
- 亮暗外观如何组织，公共语义值如何与命名样式关联。
- 动态更新的订阅范围、过渡效果和状态保留方式。
- 编辑器与运行时共享哪些模型，如何保证导出内容与业务端解析一致。

后续开新库时可将本文作为需求背景迁入，再制定新库自己的架构与协作规则。现有库继续遵守其原有规则。
